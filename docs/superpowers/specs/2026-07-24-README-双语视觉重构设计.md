# CodexKeep README 双语视觉重构设计

## 背景

当前 `README.md` 已经包含安装、首次设备、新设备、命令概览、数据模型、安全
边界、开发与发布等基础信息，但各命令的说明深度不一致。`init` 和 `remote`
相对完整，`sync`、`update`、`check` 与 `link` 仍以简短概述为主。项目也缺少
完整的简体中文镜像文档和统一的视觉表达。

本次重构要让首次访问者快速理解 CodexKeep 的用途、核心流程与安全边界，同时
让已有用户可以查到每个菜单项和命令的准确行为。视觉内容负责定位、演示和解释，
不能取代可复制命令或正文。

## 目标

- 保留英文 `README.md` 作为 npm 与 GitHub 的默认文档。
- 新增完整的简体中文镜像 `README.zh-CN.md`。
- 覆盖交互菜单及 `init`、`sync`、`update`、`check`、`remote`、`link` 的完整
  使用说明。
- 采用统一的 Midnight Sync 视觉语言，提高项目辨识度。
- 使用少量、职责明确的视觉资产，避免把 README 做成宣传海报。
- 让 GitHub 与 npm 页面上的核心信息都能正常阅读。
- 所有描述都以当前实现、CLI 帮助和测试为依据，不承诺尚未实现的行为。

## 非目标

- 不修改任何 CLI 行为、命令名称、数据格式或同步策略。
- 不增加运行时依赖或文档构建依赖。
- 不制作独立官网或交互式文档站点。
- 不自动翻译或在运行时生成 README。
- 不把视觉讨论草稿、录制临时目录或测试用用户目录提交到仓库。

## 已考虑的视觉方向

### 采用：Midnight Sync

使用深色紫蓝渐变、轻量设备拓扑、克制的状态徽章和清晰的大标题。它能同时表达
“跨设备同步”“私有 Git”“敏感数据留在本地”，并保持成熟的开源产品感。

### 不采用：终端原生

纯终端绿色和 ASCII 标题最贴近 CLI，维护成本也最低，但与普通开发者工具的
README 相似度较高，项目辨识度不足。

### 不采用：Mascot Launch

明亮插画和工具箱吉祥物更亲和，但图片资产维护成本最高，也容易弱化项目强调的
可靠性和安全边界。

三个方向是互斥选择。最终 README 只使用 Midnight Sync，不同时保留另外两套
风格。

## 双语文档结构

`README.md` 和 `README.zh-CN.md` 使用相同的章节顺序、命令示例、警告层级和
安全边界。两份文档顶部互相链接：

```text
English | 简体中文
```

中文文档不是摘要版。任何新增、删除或调整的公共命令说明都必须同步修改两份
文档。两份文档允许自然语言表达不同，但不能在行为、默认值、冲突处理和恢复
方式上出现差异。

章节顺序固定为：

1. 首屏定位；
2. 30 秒上手；
3. 终端演示；
4. 工作原理；
5. 首次设备、新设备与日常同步；
6. 完整命令说明；
7. 同步内容与安全边界；
8. 数据模型与符号链接；
9. 常见问题和失败恢复；
10. 开发与发布。

## 首屏与快速上手

首屏按以下顺序组成：

1. Midnight Sync Banner；
2. 一句话说明 CodexKeep 通过用户自己的 Git 仓库同步个人 Codex 配置；
3. npm 版本、CI、Node.js 要求和 License 等少量状态徽章；
4. 中英文切换入口；
5. 安装和首次运行命令。

快速上手必须在长篇概念说明前出现：

```bash
npm install -g codexkeep
codexkeep
```

随后用一句话说明直接运行 `codexkeep` 会打开交互菜单。高级用户仍可以直接调用
具名子命令。

## 视觉资产

视觉内容只保留三类，每类承担不同的信息任务。

### 首屏 Banner

Banner 使用轻量 SVG，放在 `docs/assets/readme/`。它包含 CodexKeep 标题、
设备到私有 Git 再到新设备的概念路径，以及少量类似 `portable config`、
`private by default` 的短标签。

Banner 不包含需要分别翻译的长段文字，因此中英文 README 可以共用。画面中的
设备拓扑只是概念定位，不承担精确描述同步算法的责任。

### 终端演示

使用一段约 10 至 15 秒的 GIF 展示：

```text
启动 CodexKeep → 选择同步配置 → 完成预检 → 同步成功
```

演示必须来自真实 CLI。录制使用隔离的临时主目录、临时 Codex 数据和测试 Git
仓库，不读取或修改真实用户主目录。演示不出现真实仓库地址、用户名、凭据、
session、token 或机器绝对路径。

GIF 只证明核心流程可用，不尝试演示所有菜单项。命令细节仍由正文负责。

### 数据流与安全边界图

README 使用 Mermaid 表达以下关系：

```text
本机可移植配置 → CodexKeep 完整预检 → 用户的私有 Git → 另一台设备
```

credentials、sessions、cache、project trust、机器路径、Codex 内置内容和插件
包从主流程分叉到“始终留在本机”的边界。英文和中文文档使用结构相同、标签分别
本地化的 Mermaid 源码。

紧邻图表的正文和“会同步 / 永不同步”对照表必须能独立说明安全边界。即使某个
Markdown 渲染器没有显示 Mermaid，用户仍能获得完整信息。

### GitHub 与 npm 兼容

npm 包页面使用根目录 `README.md`，并通过 GitHub API 按 GitHub Flavored
Markdown 渲染。GitHub 支持 README 中的 SVG、GIF 和 Mermaid，但外部渲染器
对 Mermaid 的支持可能不同。

Banner 与 GIF 保存在仓库中，README 使用指向
`raw.githubusercontent.com/HenryOoO/codexkeep/main/` 的绝对 HTTPS 地址，
避免 npm 页面因相对仓库路径无法取到未进入 npm tarball 的资源。视觉资产只
解释长期稳定的产品定位，不作为某个 npm 版本的行为合约，因此允许旧版本的
npm 页面看到当前视觉资产。

`package.json.files` 不为视觉资源扩容。安装 CLI 时无需下载 README 图片。

## 使用场景

文档提供三条场景化路径。

### 第一台设备

说明安装、运行 `codexkeep init [git-url]`、确认初始化计划和完成首次同步的
过程。明确私有仓库需要由用户预先创建，以及空仓库与有效的既有 CodexKeep
仓库分别如何处理。

### 新设备

说明安装、运行 `codexkeep init <git-url>`、克隆并验证已有私有仓库、检查计划
并恢复可移植配置的过程。强调预检和确认发生在文件变更之前。`codexkeep link`
只用于本地 `~/.codexkeep` 已存在时重新建立官方路径的符号链接，不访问网络，
不能代替新设备的初始化。

### 日常同步

建议先用 `codexkeep check` 查看状态，再根据需要运行 `codexkeep sync`。
需要升级并合并远端状态时使用 `codexkeep update`。正文必须根据实现准确说明
每条命令的拉取、提交、推送和本地应用行为，不能仅凭命令名称推断。

## 菜单与命令说明

交互菜单和命令行入口建立明确映射：

| 菜单项 | 命令 |
| --- | --- |
| 同步配置 | `codexkeep sync` |
| 升级并同步 | `codexkeep update` |
| 查看状态 | `codexkeep check` |
| 连接或查看远程仓库 | `codexkeep remote` |
| 连接当前设备 | `codexkeep link` |
| 初始化 | `codexkeep init` |

直接运行 `codexkeep` 的交互入口也需要单独说明。每个具名命令使用相同的小节
模板：

- **用途**：适用时机；
- **调用**：可复制的命令和参数；
- **网络**：是否访问 Git 远端或其他网络服务；
- **改动**：可能修改的本地和远程内容；
- **确认**：交互提示和 `--yes` 的边界；
- **冲突**：检测到不同内容或 Git 状态时的处理；
- **恢复**：失败后保留什么，以及安全的下一步。

命令章节以代码、CLI 帮助和现有测试为事实来源。若当前 README 与实现不一致，
本次只修正文档；任何需要改变 CLI 的差异都作为后续工作提出，不在本次静默
扩展范围。

## 安全说明

安全章节使用对照表清楚区分：

- 支持同步的个人 skills、agents、`AGENTS.md`、可移植配置和经过筛选的插件
  声明；
- 永不同步的 credentials、sessions、cache、project trust、机器路径、Codex
  内置内容和插件 bundles。

正文解释完整预检、确认前零文件改动、可恢复写入、备份以及符号链接的含义。
不能只使用“安全”或“隐私优先”等宣传词，必须说明具体边界和失败后的保留状态。

## 常见问题与恢复

常见问题至少覆盖：

- 为什么必须使用私有 Git 仓库；
- 新设备应该使用 `init` 还是 `link`；
- 本地或远端存在不同内容时会发生什么；
- 同步失败后是否可以重试；
- 为什么 credentials、sessions 或插件 bundles 不会出现；
- 如何确认当前设备连接的远程仓库；
- 自动确认 `--yes` 会跳过哪些提示，以及哪些安全校验仍不会跳过。

恢复说明只提供产品实际支持且不会丢失数据的操作。涉及删除、强制覆盖或手工
修改内部仓库的命令不作为常规修复路径。

## 开发与发布

开发章节保留 Node.js 22 及以上版本和 pnpm 要求，并提供：

```bash
pnpm install
pnpm check
pnpm test
pnpm build
```

发布章节只暴露统一入口：

```bash
pnpm release
```

说明该命令通过 `bumpp` 交互选择语义化版本，创建并推送 Release 提交和 tag，
再创建 GitHub Release，由 GitHub Actions 使用 npm Trusted Publishing 完成
发布。README 不重复实现文档中的所有内部预检细节，只链接到适合维护者阅读的
说明。

## 降级与错误处理

- 图片加载失败时，替代文本、紧邻说明和命令仍能表达完整用途。
- Mermaid 未渲染时，安全对照表和正文仍是权威说明。
- GIF 录制或压缩无法达到清晰度和体积要求时，使用同风格的静态终端截图，
  不提交巨大或模糊的动画。
- 中英文内容无法同时准确完成时，不先合并其中一份；两份文档作为同一个改动
  验收。
- 文档核对发现实现行为不清晰时，优先引用现有测试确认；仍无法确认则暂停对应
  段落，不猜测行为。

## 验收

实现完成后必须验证：

- 两份 README 的章节、命令、示例和安全边界一一对应；
- 桌面和移动宽度下没有横向溢出、内容重叠或不可读的小字；
- Banner 是轻量 SVG，GIF 清晰且体积受控；
- 图片、语言切换和文档内部链接有效；
- Mermaid 使用 GitHub 当前支持的语法；
- README 中的所有命令与 CLI 帮助、实现和测试一致；
- `pnpm check`、`pnpm test` 和 `pnpm build` 全部通过；
- `npm pack --dry-run` 中包含正确的根目录 `README.md`，且不包含视觉草稿、
  录制临时文件或真实用户数据。

浏览器视觉讨论生成的 `.superpowers/` 目录加入 `.gitignore`。这只防止本地
设计草稿进入版本控制，不改变包内容或运行时行为。
